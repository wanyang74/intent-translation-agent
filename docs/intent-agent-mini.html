Intent Translation Agent · Design draft v0.5 · updated 2026-10-12

Intent Agent Mini

The smallest first version: take what a person can already do on a consumer site's frontend and turn it into a conversational agent flow that can loop and compare at scale. It only sends requests the frontend already sends. It doesn't touch the backend and doesn't place orders. The platform is general: everything it knows about a site comes from that site's pack, and Carvana is the first.

Stage Prototype design First site pack carvana.com Next Airlines · brokerages Platforms Web · iOS (Android next) Operations Read-only

Scope and boundaries

The ceiling is what a person can do on the site's frontend. The agent adds scale and automation: on Carvana, a person checks one car's quote at a time, while the agent can pull 50 and compare them. Every call is still one the frontend would send.

In this version, on Carvana first

  • Turn a natural-language goal into structured search filters
  • Exhaustive search across filter combinations
  • Batch-fetch delivery times, then quotes and GAP waiver prices for the finalists
  • Filter on combined conditions the site's filters can't express, such as "under $40k estimated total and available before the weekend"
  • Build comparison tables with deep links back to the site

Not in this version

  • Any write action: favorites, holds, orders, bookings, trades, payment
  • Parameters or endpoints the frontend never uses
  • Server-side calls, or getting around bot protection such as Cloudflare
  • External agents and cross-platform parity (the design leaves room for them)
  • On Carvana: showing, filtering or ranking by monthly payment or APR
  • Memory across sessions

Boundary rules, enforced in code

  1. Parameters only take values the frontend can produce. Allowed values come from the site's own responses, and page sizes stay at the site's own. On Carvana, filter values come from the facets response, pageSize stays at 24 and requestedFeatures is copied from the frontend.
  2. Only the tracking fields an endpoint requires, as the site pack lists them, with fresh random IDs per session, never a real visitor's ID. On Carvana, quote and suggest need a client ID, and suggest also needs a visitor ID. See D4.
  3. Usage is capped. One shared budget per task, per session and per day, drawn on by direct, parallel and script calls alike, and one rate limit. The site pack sets both; Carvana's are 60 calls per task and 1 call per second. Repeated requests are served from cache.
  4. Only read tools are registered. The site pack marks each tool as a read or a write, and its policy says whether writes are allowed at all: none in the mini version.
  5. Only known IDs. Tools and the UI accept only IDs of the right kind that a tool returned in this session, or the item on screen, and that haven't expired.
  6. The person takes the last step. When an action is needed, the agent gives a deep link and the user clicks through on the site.

The harness is split by where each part runs. The client runs the tools and the server runs the agent loop, so API keys never reach a device. A language-neutral contract, produced at build time, connects them. Each dashed block below is a separately owned part, labeled with its language.

One request, step by step

  1. The user states a goal
    overlay, SwiftUI sheet or Compose sheet
  2. The client sends the conversation and page context to the agentic brain
    client → server
  3. The agentic brain calls the model
    server → LLM provider
  4. The agentic brain returns tool calls or a script
    server → client
    Each tool call goes out as soon as the model finishes writing it, without waiting for the rest of the response.
  5. The tool runtime checks boundaries and calls the site's API
    core.js → the site's APIs
    The request goes out with the page's or app's own session. Scripts run in the platform's sandbox and can only call registered tools.
  6. The site's API responds to the tool runtime
    the site's APIs → core.js
    Steps 5 and 6 are one request and its response. A script can repeat them many times without involving the agentic brain. If the agentic brain marked the call for direct rendering in step 4, Execute hands the result straight to Respond, which shows it right away; steps 7 and 8 then run in the background.
  7. The tool runtime sends the results, or a script's summary, to the agentic brain
    client → server
    The model needs the results to decide the next step or write the answer. Steps 3–7 repeat until the step budget runs out or the model has an answer.
  8. The agentic brain returns the answer and UI components; each platform renders them natively
    server → client
    They arrive as presentation tool calls. Brain link hands them to Execute, which validates them like any other tool call and passes them to Respond. Presentation tools carry only IDs and a layout; Execute fills in every displayed field from this session's tool results.
  9. The user finishes on the site's own page or screen
    deep link (web) or app action (iOS, Android)

  • No change (gray): Execute's tool registry, the agentic brain, LLM providers, the contract, discovery and generated code.

MCP vs A2A: what we can keep consistent

A2A keeps our decisions consistent, MCP keeps our data consistent, and neither controls what the user finally sees. Widgets and approval handoff are how we protect that last step in both modes.

Where A2A's consistency stops

  • Input: the agent rewrites the user's request before sending the goal. It may drop details, add things from its own memory, or split one question into several tasks.
  • Follow-ups: when we ask a question such as the zip code, the agent may answer from its own memory instead of asking the user.
  • Output: the agent decides how to show our result. It can summarize, re-rank, mix in a competitor's results, or leave out our disclaimers.

What stays the same in both modes

  • Data: the same Execute, Fetch and boundary checks run either way, so prices and availability match our own app.
  • Writes: anything that changes state, such as holding a car, booking a flight or placing a trade, finishes with approval in the enterprise's own trusted UI.

Levers we still have in MCP

Recommended approach

  • MCP as the default, with task-level tools and widgets. Agent platforms often prefer it because they orchestrate across brands, for example comparing several dealers.
  • A2A, or one MCP tool that hands the goal to the site's own agent, for flows where the brand's logic matters most: financing, returns, fare rules, account questions and other policy-heavy topics.
  • In both modes, protect the final experience with widgets for what the user sees and approval handoff for anything that changes state.

Key decisions

  • The server drives the loop; the client runs the tools. Prompts and skills stay on the server, and the same agentic brain can later serve external agents.
  • We own the loop and the tool runtime. AI SDK Core is used only for model calls. Full frameworks such as Mastra or LangGraph wait until we need durable tasks, memory or multiple agents, and stay behind our own interfaces.
  • core.js has no Node dependencies. It touches the outside world only through the Host interface, so the same bundle runs in a page, in JavaScriptCore, in QuickJS, and on the gateway.
  • Scripts run in a real sandbox on each platform. A plain Web Worker isn't enough, because it can call any URL.
  • The contract is the source of truth. Types and validators for every language are generated from it, never written by hand.
  • Presentation tools take IDs, not content. Execute fills every displayed field from tool results, so the model can't put a made-up price on screen.
  • Client checks guard against the model; servers guard money and state. See D3.
  • The platform never names a site. Everything site-specific is data in a site pack, checked against one format, and a second, synthetic site pack runs through every test. See D5.

Script layer

For batch tasks, the LLM doesn't call tools one at a time. It writes a short script that runs in a sandbox, calls the tools, and returns only IDs and a short summary. Scripts use what search already returns and the bulk availability call first, and quote individual cars only for finalists.

// Generated by the LLM and run in a sandbox. It can only call the site pack's tools, and the boundary checks still apply.
const { vehicles } = await tools.search_vehicles({ make:"Tesla", model:"Model Y", drive_types:["Awd"], zip5:"94402" });
const { dates } = await tools.get_delivery_dates({ vehicleIds: vehicles.map(v => v.vehicleId), zip5:"94402" });  // one bulk call
const deadline = "2026-10-11T06:59:59Z";                                          // end of Saturday, from the brain's clock
const soon = new Set(dates.filter(d => d.delivery && d.delivery.date <= deadline).map(d => d.vehicleId));
const picks = vehicles
  .filter(v => soon.has(v.vehicleId))
  .filter(v => v.estimatedTotal <= 40000)                                 // derived field, the site pack's formula
  .sort((a, b) => a.estimatedTotal - b.estimatedTotal)
  .slice(0, 5);
return { ids: picks.map(v => v.vehicleId), checked: vehicles.length };      // IDs, not content

The model then calls present_items with the returned IDs, and Execute fills in each card. Scripts can read the session's ID set but can't add to it.

Deep links

Each site pack declares link templates for the site's own pages. Carvana's search results pages are /cars/filters?cvnaid=…, where cvnaid is the filters as base64 JSON, and its vehicle pages are /vehicle/{vehicleId}. Every result the agent returns carries a link that opens the same results page or that item's page on the site.

Safety and grounding

Rules that keep answers true and safe. They're enforced in code, not in the prompt, because prompt rules can be skipped through injection or a bad model output.

Grounded answers: only known IDs

  • Every ID a tool returns is recorded for the session with its kind and, where the site's IDs expire, its expiry. The site pack says where the IDs are in each result; Carvana's are vehicles, routes and suggestions.
  • Tool calls and presentation calls may only use recorded IDs of the right kind that haven't expired. Made-up IDs, IDs pasted by the user and IDs planted in review text are refused with an error that says where valid IDs come from.
  • The model never writes content into the UI. Presentation tools take IDs, and Execute fills in every field from stored results. Derived numbers come from named formulas and are labeled as estimates.
  • Both sides check. The agentic brain refuses presentation calls with unknown IDs before sending them, and core.js checks again. Scripts can read the ID set but can't add to it.

Required wording and regulated figures

  • Notices are data. The site pack stores each notice's approved wording, versioned, with the fields it must appear next to. core.js shows it exactly whenever one of those fields is on screen; the model only picks which notice applies.
  • On Carvana, the mini version doesn't show monthly payments or APR, and doesn't filter or rank by them; they are hidden fields in the site pack. It shows prices, estimated taxes and fees, delivery dates and GAP waiver prices.
  • Why: under US lending ad rules (Regulation Z), stating a payment amount can require more disclosures, such as APR, term and down payment. Carvana shows its own wording next to these numbers, and an agent repeating them without it could fall short. This needs review by counsel.
  • When enabled later: Carvana's wording becomes a notice. core.js inserts it exactly, from the stored and versioned copy, and evals compare it character for character. Neither the model nor the UI can reword it.
  • Other sites: US airfares are shown with all taxes and fees (the price-display policy), and brokerages bring their own disclosures as notices.

Untrusted text

One sanitizer in core.js handles all text we don't write: reviews and other free text from the site (on Carvana, owner reviews and free-text vehicle fields), the page context sent in step ②, and goals from external agents. It removes control and bidirectional characters, fake conversation turns, fake tool calls and fence lookalikes, caps the length, and wraps the result in a fence with a fixed label. The system prompt says fenced text is material to report on, never instructions to follow.

Caps that hold under retries and parallel calls

  • One shared budget per task, per session and per day, set by the site pack (Carvana: 60 calls per task). Direct calls, parallel calls and calls from scripts all draw from it, so retries and parallel steps can't stack past a limit.
  • One rate limit for the whole session, from the site pack (Carvana: 1 call per second), so parallel calls queue instead of bursting.
  • Exhaustive searches can hit the budget. On Carvana, 694 matching cars is 29 pages, and pages plus availability would use about 58 of 60 calls. Filter on search fields first, fetch availability only for candidates, and ask the user to narrow the search when the results are too many.
  • For future writes: caps apply to the resulting state, writes in a session run one at a time, and limits are checked again when a change is applied.

Latency and caching

Task time is the sum over steps of model time plus tool time. Our design adds one client round trip per step (D1) and the site's rate limit (Carvana: 1 call per second), so we cut the number of steps and calls, overlap what we can, and show progress.

Fewer, faster steps

TechniqueHow
Use what we already haveOn Carvana, search results include price and estimated taxes and fees, and the availability call takes a list of cars. Phase 0 confirmed that search and quote return identical numbers for the same car, so quote calls are only for the quote card and the GAP waiver.
Parallel callsIndependent calls in one step run together, within the shared budget and rate limit.
Send tool calls earlyThe agentic brain streams the model's output and sends each tool call to the client as soon as its arguments are complete. The prompt asks for the slowest call first.
Scripts for batchesOne round trip runs dozens of calls and returns a short summary.
Context up frontStep ② carries the page context, and the matching skill loads before the first model call.
Fast pathSimple lookups render straight from tool results; steps ⑦ and ⑧ run in the background.

Example: "AWD Model Y under $40k by Saturday." Quoting 30 cars one by one would take 15–30 seconds at the rate limit. With search-result prices and one bulk availability call, the same answer needs 2 calls. Exact quotes come later, only for the cars the user opens.

Feeling fast

  • Progress lines while tools run, built from the tool arguments: "Checking delivery dates for 24 cars…"
  • Cards stream in as Execute fills them, instead of appearing all at once at the end.

Prompt layout and caching

Prompt caching works on the beginning of the request, so the prompt is ordered from most stable to least stable. The target is a 90–99% cache hit rate; on Claude, cached input costs about a tenth of the fresh price.

SegmentContentsChangesCaching
1 · GlobalSystem prompt (grounding, presentation, safety and brand rules) and all tool and presentation-tool definitionsOnly when we releaseIdentical for every session; cache breakpoint at its end
2 · SessionConversation so far, tool results, and skills, which load as tool resultsGrows during the sessionBreakpoint moves to the end of each new user turn
3 · VolatilePage context and current timeEvery turnNot cached; a tagged block at the end of the newest user turn

A timestamp or the current page at the top of the system prompt would break the cache on every request. AI SDK Core passes Claude's cache breakpoints through provider options; most other providers cache matching prefixes automatically. Cache hit rate is tracked per step and gated in CI.

Agentic brain

Neither page scripts nor the app can hold an API key, or anyone could extract it. So the agentic brain runs on our server: it receives the conversation and page context, runs the agent loop, calls the model, and sends tool calls to the client to run. It never calls the site directly (D1).

All three platforms share it. It is also where the gateway starts later: logging, audit, quotas and external-agent access will live here.

Prompt and skills

One agent with skills: no router and no subagents. What goes in the prompt depends on how often it's needed. Anything about a third or more of conversations use goes in the system prompt, and the rest becomes a skill that loads on demand. Evals confirm the split. Skills come with the site pack; Carvana's are below.

Memory

Out of scope for the mini version. Users are anonymous, and nothing is kept after the session ends. When we add it, it follows the guide:

  • Facts are typed records in our own database (key, short value, category, source session), not a text profile.
  • A separate background step extracts them after a turn. It reads only what the user and the agent said, never tool results, so listing text can't become "facts" about the user. There is no save-memory tool.
  • Reading has three layers: a small set always in context, facts prefetched per turn from the same signals that load skills, and a lookup tool for the rest.
  • A validator limits what can be stored. Users can view, correct and delete facts, facts expire, and memory can be turned off per deployment.

Evals and testing

Two kinds of checks: functional tests that the code works, and evals that the agent's answers are right. Each site's recorded fixtures make both repeatable without touching the site's servers. The Verification plan describes how each module is checked on its own before it's integrated.

Snapshot evals

Each case builds a state directly: the conversation so far and recorded tool results. It adds the user's next message, runs the agent, and grades the result: the final state, the rendered answer and the last tool call's arguments. It doesn't grade the exact path the agent took, which would make cases brittle.

Every case also checks that each price, date and fact on screen traces to a tool result in the snapshot, that missing data is stated rather than invented, and that no internal IDs appear in the text. Each site pack brings its own cases; the examples below are Carvana's.

CategoryExample cases
Core requests"AWD Model Y under $40k by Saturday"; questions about a car's features; two requests in one message
Context-dependent"The second one" after a list; "same but 2023"; a user who changed their mind earlier in the conversation

  • A negative for every positive: "should refuse" paired with "should answer", and "should ask" paired with "should just do it". Missing negatives are the most common gap.
  • Messy starting states: long conversations, contradictions and changed constraints, not only clean starts.
  • Simulated users only to find gaps; each finding becomes a snapshot case.
  • Start with about 50 cases for search-and-compare, then 50–100 per flow, written with product and legal reviewers. Once there's real traffic, tricky sessions become new cases.

CI gates and model choice

  • Every change runs the high-traffic cases and all safety cases, plus cases for whatever changed: a skill's cases and its neighbors', and every case that calls a changed tool. The full suite runs nightly and before each release.
  • Gates: pass rate over several trials, cache hit rate, and cost per completed task.
  • Model and effort level are chosen by running the suite across candidates against set budgets for quality, p50 and p99 latency, and cost per completed task. Prompts are tuned for each candidate before ruling it out. Start with a Sonnet-class model for this consumer flow; if tasks take more than about five steps, try a smarter one.

Operations

Our tools depend on frontend endpoints a site can change without notice, so we need to switch things off quickly and roll changes out carefully.

PracticeHow
Off switchesEach site's tools and skills can be turned off one by one, remotely. core.js reads a signed config at session start; a turned-off tool returns the "unavailable" error, so the agent answers without it. No app release needed.
Endpoint change monitorResponses are validated against the site pack's schemas. Repeated mismatches or new errors turn the tool off automatically and alert its owner.
Gradual rolloutPrompt, skill and core.js changes go to a small share of sessions first, per customer. We compare task completion, errors, cache hit rate and cost per task before widening.
FreezesNo agent changes right before a customer's peak periods, such as holiday sales.
OwnershipOne owner per tool and per skill. Shared prompt sections have a platform owner. Every change ships with its own eval cases, including negatives and cases at the boundary with neighboring skills.
Signed bundlescore.js updates are signed and checked before loading, because they run inside the user's page or app.

Verification plan

The goal is to catch a module's bugs while it's still on its own, before other modules depend on it. Every module is tested against the shared contract, not against its neighbors. Every dependency has a fake, so each module can be tested alone and deterministically. Each integration step swaps exactly one fake for the real thing, so when something breaks there's only one suspect.

Code bugs and model behavior are kept apart. Code paths are tested with FakeModel, deterministically, and answer quality is judged only by evals. A flaky model answer never hides a code bug, and the reverse.

From day one

  • A trace ID on every message and call (steps ② to ⑧), plus a development log of inputs and outputs at every module boundary. When a bug appears late, the trace shows which module first produced the bad value.
  • Every bug becomes a test at the lowest level that could have caught it, and an eval case if it's agent behavior.
  • A weekly live check runs a few real calls per site and compares them with the fixtures, so outdated fixtures are caught early instead of passing silently.
  • Three things to avoid: building the UI first, testing core.js only in Node, and using the live LLM in unit tests.

Technical design decisions

A log of questions we've settled, with the reasoning and what would make us revisit them.

D1

Why does the client call the site's APIs instead of the agentic brain?

Decided 2026-10-09
Decision
The tool runtime on the client sends requests to the site (steps ⑤ ⑥). The agentic brain never calls the site directly in the mini version.
Alternative considered
The agentic brain calls the site's APIs itself, which removes the client from the tool loop and saves a round trip per agentic brain step.
Rationale
  • Stays within "what a human can do." A client request carries the user's own session, IP, browser or app, and Cloudflare clearance, so it is the user browsing. The same request from our server is unauthorized automated traffic.
  • The server would be blocked. On Carvana, Cloudflare already returned 403 to curl for the site's pages. All users' traffic from a few server IPs would be rate-limited quickly.
  • User sessions stay on the device. Signed-in tools (on Carvana, favorites, pre-qualification and trade-in; on an airline, trips) would otherwise require holding users' session tokens on our servers.
  • The app needs a client runtime anyway for in-app actions, so fetches use the same execution model.
Cost we accept
One extra client ↔ agentic brain round trip per agentic brain step (④ out, ⑦ back), roughly 100–300 ms (estimate) against several seconds of model time. Scripts reduce it: one ④ can run dozens of ⑤ ⑥ pairs and return a single ⑦ summary. Page context sent in ② saves a step.
Revisit when
  • An enterprise authorizes server-side access: official credentials or allowlisted IPs, and user identity through OAuth token exchange.
  • We add external agents (MCP), which have no client runtime of ours.
  • Measured latency of the extra round trip turns out to matter.
Then the same core.js runs on the gateway with Host.request pointed at the enterprise backend. Likely end state: a per-tool choice in the site pack, with public cacheable reads (search, facets) on the server and session-bound tools and app actions on the client.
D2

Why do tools combine several of the site's calls on the client instead of one backend endpoint?

Decided 2026-10-10
Decision
In the mini version, task-level tools and scripts combine several frontend calls inside core.js, for example Carvana's availability, then pricing, then GAP waiver.
Alternative considered
One backend endpoint per task that answers the whole question, which is what the guide recommends.
Rationale
We have no backend access in the mini version, and the frontend endpoints are the only allowed surface (D1). Search-result fields and the bulk availability call keep the number of calls low.
Cost we accept
More calls and more time per task, orchestration in our code that the site's backend could own, and breakage when endpoints change, which the endpoint change monitor and off switches cover.
Revisit when
An enterprise grants server access. Then we ask for combined endpoints for the top tasks, such as "price and delivery date for these 20 cars at this zip code."
D3

What do client-side checks protect against, and what must a server enforce?

Decided 2026-10-10
Decision
Checks in core.js protect against model mistakes and prompt injection. Anything that protects us or the enterprise is enforced on a server that we or the enterprise control.
Alternative considered
Treat the core.js checks as the only enforcement.
Rationale
core.js runs on the user's device, where the user can change it. For read-only calls made with the user's own session, that's acceptable: they could make the same calls by hand. It isn't acceptable for our costs or for anything that changes state.
Server-side enforcement
  • The agentic brain enforces LLM quotas and per-user and per-day limits.
  • It accepts tool results only for calls it issued, and refuses presentation calls with unknown IDs.
  • Future writes use staged changes with server-issued IDs, approval in the enterprise's own UI, and limits checked again at apply time on the enterprise backend or our gateway.
Revisit when
We add any write action, or the gateway starts serving external agents. Then every check also runs on the server.
D4

Which of the frontend's tracking fields do our requests send?

Decided 2026-10-12
Decision
Only the fields an endpoint requires, as its site pack lists them, with fresh random IDs per session. On Carvana, phase 0 found that search, facets and reviews need none, quote needs a client ID, and suggest needs a client ID and a visitor ID. Where we haven't tested without them (the availability headers), we send the frontend's set, with fresh IDs.
Alternative considered
Copy the frontend's full analytics block, or reuse the visitor ID from the user's own browser.
Rationale
We stay within what the frontend sends without impersonating a real visitor or adding more to the site's analytics than needed. Fewer fields also means fewer ways for an analytics change on the site's side to break us.
Cost we accept
If a site starts requiring more fields, calls fail until we update its site pack; the contract tests and the change monitor catch that. Our sessions look like new visitors in the site's analytics.
Revisit when
An enterprise integrates with us officially. Then we agree with them how agent traffic identifies itself, for example a dedicated client ID.
D5

Why is everything about a site kept in its site pack, apart from the platform?

Decided 2026-10-12
Decision
The platform never names a site: the protocol, presentation tools, errors, config, the site-pack format, the checks and code generator, the testkit, and later core.js and the agentic brain. Everything site-specific is a site pack in sites/<id>/: entities, endpoints, tools, forms, notices, policies, deep links, skills, schemas, fixtures, example conversations and research. A test fails if a platform file names a site.
Alternative considered
Build for Carvana first, and generalize when the second site arrives.
Rationale
  • Site assumptions spread early. By phase 1, Carvana's names were already in the protocol's tool list, the presentation tools (present_vehicles, present_quote) and the error codes. Every later module would have built on them.
  • The next sites differ in ways Carvana doesn't show: signing in, prices that expire, forms and required wording. See What airlines and brokerages need.
  • A second site pack keeps it honest. Demo Flights, a made-up airline, runs through every platform test, so a Carvana-only assumption fails a test instead of showing up at the next customer.
  • External agents need the same split. The gateway publishes each site's tools from its site pack.
Cost we accept
An extra layer: the platform reads tools, IDs and rules from data instead of code. The validators one app ships grew from 36 KB to 48 KB, minified and gzipped, against a 60 KB budget. Site packs also carry a little code: fixture hooks now, and parsers such as the vehicle page's later.
Revisit when
A real site needs something the site-pack format can't express: then we extend the format rather than special-case the platform. Or the code in site packs grows beyond small adapters: then it gets its own interface and tests.
